# decision-layer-kitchen — HUD managed environment

Marketplace packaging for Second Nature Labs' **decision-layer kitchen task**:
a hidden-state household task where the correct next action cannot be
determined from the initial observation. This directory is a binding of the
unmodified `kitchen_task` package (`decision-layer/kitchen_task/`) onto the HUD
v6 environment protocol.

| | |
|---|---|
| Environment name | `decision-layer-kitchen` |
| Version | `0.1.0` |
| Tasks | 3 (`dlk-01` … `dlk-03`) |
| Capability | `mcp` — one tool, `act(action)` |
| Reward | grader total (0–100) / 100, terminal |
| Backend | symbolic (pure Python standard library) |
| Image | `python:3.12-slim`, ~no runtime deps beyond the HUD SDK |

## What the agent sees

*"Put the leftovers away in the fridge."* One of three hidden states is seeded
per episode. A fixture's interior is observable **only while its door is
open**, so `nominal` and `fridge_full` are byte-identical at t=0 (pinned by
test). The agent must inspect, update its belief, then intervene; acting on the
default assumption is the designed trap.

The action grammar is unchanged: `open` / `close` / `pick` / `place` /
`discard` / `declare` / `done`, one free-text action line per call, and every
action — including one that fails to parse — costs one toward the parsimony
budget. The grader is the published three-way split (inference 40 / parsimony
25 / intervention 35) with its anti-cheat rules intact: the guessing cap, the
fresh-food discard debit, parsimony withheld when the primary intervention
never landed, and negative parsimony past 2× the expert action count.

## Execution is oracle by design

A valid primitive is realized by setting substrate state directly. The robot
arm never actuates. This is the product thesis, not a shortcut: the system
under evaluation is the **decision layer** (inspect → infer → intervene),
isolated from motor execution — the same separation no-start-env draws between
diagnostic reasoning and wrench-turning. There is no motion planning, no
grasping, and no physics stepping, and the listing says so up front.

## Symbolic backend in production, RoboCasa as validation

The managed environment runs the **symbolic** backend: a pure-Python kitchen
state model with no simulator. The RoboCasa/MuJoCo backend is the *validation*
substrate and is deliberately **not** a v0.1 production dependency — it needs
robosuite master from source and roughly 10 GB of downloaded kitchen assets
(~23 GB extracted), none of which is in this image or any uploaded bundle.

The substitution is sound because the grader queries only the `Backend`
protocol, and in the sim backend those answers are computed from geometry
(object poses against region bounding boxes, door joint angles). The scripted
expert scores 100.0 on all three variants on **both** backends, and the
adversarial teleport probe caps at 40.0 on both. `decision-layer/handoff/` and
`decision-layer/AUDIT.md` carry that evidence; `decision-layer/scripts/validate_sim_backend.py`
re-runs it against a real RoboCasa install.

`vendor/kitchen_task/backends/robocasa_backend.py` ships in the mirror for
provenance but is never imported by the managed environment and would fail to
import in the image (no numpy, no robosuite).

## Task ids are opaque on purpose

A variant name *is* the answer the agent must `declare`. Client-visible task
specs therefore carry `{"task_id": "dlk-01", "seed": 0}` and nothing else; the
id→variant map lives server-side in `adapter_core.TASK_VARIANTS`.

| task | seed |
|---|---|
| `dlk-01` | 0 |
| `dlk-02` | 0 |
| `dlk-03` | 0 |

Seed 0 is the published configuration: the expert action-count baselines that
parsimony is scored against are pinned at this seed.

## Layout

```
env.py          HUD Environment: mcp capability + the put_away task template
tasks.py        the three task rows (opaque slugs, seed column)
adapter_core.py the whole adapter — imports kitchen_task, no hud/fastmcp imports
tasks.json      portable taskset manifest (hud.Taskset.to_file)
pyproject.toml  dependencies (hud only) + the uv lock's project metadata
uv.lock         generated by `uv lock`; the image installs from it
Dockerfile.hud  container definition, with a build-time health check
vendor/         gitignored mirror of decision-layer/kitchen_task, staged by
                deploy/hud/stage.py
```

## Build and test

```bash
python deploy/hud/stage.py
.venv/bin/python -m pytest deploy/hud/tests -q
.venv-hud/bin/hud task list -s deploy/hud/decision-layer-kitchen
.venv-hud/bin/python deploy/hud/scripts/protocol_check.py --env decision-layer-kitchen
```

Container:

```bash
cd deploy/hud/decision-layer-kitchen
docker build --no-cache -f Dockerfile.hud -t sn-decision-layer-kitchen-hud:0.1.0 .
```

```bash
.venv-hud/bin/python deploy/hud/scripts/protocol_check.py --env decision-layer-kitchen --runtime docker
```

RoboCasa validation (needs the sim venv described in `decision-layer/README.md`;
not required to run or deploy the managed environment):

```bash
.venv-sim/bin/python decision-layer/scripts/validate_sim_backend.py
```

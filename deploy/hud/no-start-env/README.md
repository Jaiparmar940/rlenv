# no-start-env — HUD managed environment

Marketplace packaging for **no-start-env**, Second Nature Labs' vehicle
electrical no-start diagnostic environment. The environment itself is not
defined here: this directory is a binding of the unmodified `nostart` package
(`src/nostart/`, the same code the published benchmark and the OpenReward
listing run) onto the HUD v6 environment protocol.

| | |
|---|---|
| Environment name | `no-start-env` |
| Version | `0.1.0` |
| Tasks | 5 (`ns-01` … `ns-05`) |
| Capability | `mcp` — seven tools |
| Reward | grader total (0–100) / 100, terminal |
| Image | `python:3.12-slim`, ~no runtime deps beyond the HUD SDK |

## What the agent sees

A customer complaint and seven shop tools: `scan_dtcs`, `read_pid`,
`measure_voltage`, `visual_inspect`, `replace_part`, `attempt_start`, `finish`.
Voltages are computed from a resistance-network model — never hand-authored —
so a probe that would mislead a real technician misleads the agent in the same
way. The grader reads true world state, not the agent's claims.

Prompt, tool descriptions, tool JSON schemas and observation bytes are the ones
the published run used. See `adapter_core.py` for the parity contract and
`deploy/hud/tests/test_no_start_hud_parity.py` for the tests that hold it.

**One documented difference from the Inspect run.** Inspect sends a system
message and a user message; HUD's `tasks.start` returns a single prompt string,
so the two are joined with a blank line. `NoStartSession.prompt_blocks()` keeps
them separate for harnesses that have a system role. This is the same
single-channel concession the OpenReward listing documents.

## Task ids are opaque on purpose

A scenario id names its own answer (`easy_dead_battery`). Client-visible task
specs therefore carry `{"task_id": "ns-01", "tier": "easy"}` and nothing else;
the id→scenario map lives server-side in `adapter_core.TASK_SCENARIOS` and is
identical to the OpenReward listing's, so results are comparable across
marketplaces. Tier is carried because it is non-identifying and useful for
curricula.

| task | tier |
|---|---|
| `ns-01` | easy |
| `ns-02` | medium |
| `ns-03` | medium |
| `ns-04` | hard |
| `ns-05` | hard |

## Layout

```
env.py          HUD Environment: mcp capability + the diagnose task template
tasks.py        the five task rows (opaque slugs, tier column)
adapter_core.py the whole adapter — imports nostart, no hud/fastmcp imports
tasks.json      portable taskset manifest (hud.Taskset.to_file)
pyproject.toml  dependencies (hud only) + the uv lock's project metadata
uv.lock         generated by `uv lock`; the image installs from it
Dockerfile.hud  container definition, with a build-time health check
vendor/         gitignored mirror of src/nostart, staged by deploy/hud/stage.py
```

`vendor/` exists because `hud deploy` tarballs this directory and nothing above
it. It is a build artifact, not a fork: `deploy/hud/stage.py --check` (and a
parity test) assert it is byte-identical to `src/nostart/`.

## Build and test

From the repository root, with the HUD SDK on a Python 3.11/3.12 interpreter
(`.venv-hud` in the notes below):

```bash
python deploy/hud/stage.py                                  # mirror src/nostart -> vendor/
.venv/bin/python -m pytest deploy/hud/tests -q               # adapter parity
.venv-hud/bin/hud task list -s deploy/hud/no-start-env       # task discovery
.venv-hud/bin/python deploy/hud/scripts/protocol_check.py --env no-start-env
```

Container:

```bash
cd deploy/hud/no-start-env
docker build --no-cache -f Dockerfile.hud -t sn-no-start-env-hud:0.1.0 .
```

```bash
.venv-hud/bin/python deploy/hud/scripts/protocol_check.py --env no-start-env --runtime docker
```

Deploying to HUD (needs `HUD_API_KEY`, and is a human decision — see
`docs/datavendor_packaging.md`):

```bash
hud deploy deploy/hud/no-start-env
```
